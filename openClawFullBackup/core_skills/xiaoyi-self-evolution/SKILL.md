# Xiaoyi-Self-Evolution

目标：将历史经验固化到文件中，持续提升系统能力

**硬性约束1：当需要进化时，你必须先输出纯文本审批提示等待用户审批，禁止直接修改目标文件，禁止自行确认进化**

**硬性约束2：自进化判断、进化准备、重复/冲突检测、创建待进化项只能静默执行，禁止向用户进行展示。**

**硬性约束3：回复用户时，严格遵循给定格式**

## 自进化判断

先判断当前对话是否通过自进化标准。

### 通过标准
**会话类型硬性条件**（必须满足）：
- 当前是主会话，不是 sub-agent，不是 cron，不是 heartbeat/system-only 轮次
  **会话内容通过条件**（满足任意一条即可）：
- `explicit-instruction`：用户的回复中包含“下次应该”、“你应该”、“以后都这样做”、“记住”、“注意”等强烈建议词汇，且伴随明显的行为纠正、流程规范化或交付标准设定的指导动作
- `workflow`：出现可复用、非一次性的多步骤方法，特别是用户指导了很多次改进方向后
- `struggle`：大约 `>=5` 次 tool call，或 `>=1` 次失败/重试后才成功

若只是"可能有点价值"，但证据不够明确，直接放弃本次进化流程，按正常对话回复用户，不做任何进化相关输出。

## 进化准备

若通过自进化标准，完成以下自进化准备工作：

1. 提炼证据：
    - 记录 1-3 条最关键的用户原话
    - 记录工具踩坑摘要
    - 记录哪些经验值得复用

2. 选择目标文件

选择最合适的文件写入内容：

写入 `AGENTS.md`：

- 面向未来所有类似任务的行为规则
- agent运行的安全边界
- 协作方式
- 任务执行顺序
- "以后先做 X，再做 Y" 这种全局 workflow 规则

写入 `TOOLS.md`：

- 某个工具的固定坑点
- 环境路径、命令参数、平台差异
- 外部工具如何正确使用
- "这个命令必须带某参数，否则会失败" 这种工具使用经验
- 使用什么工具或者技能能够帮助更好完成任务

写入 `MEMORY.md`：

- 用户明确表达的稳定偏好
- “做什么事用什么skill”这种skill使用偏好
- 长期有效的项目偏好
- 长期有效的沟通风格要求
- 明确、可持续复用的事实

新建 `SKILL.md`：

- 可以独立复用的多步骤 workflow
- 有明确触发场景、步骤、输入输出、坑点
- 已经超出一条规则，接近"操作手册"的内容

**你只能从以上文件中进行选择，禁止把任何其它文件作为进化目标**

## 重复/冲突检测

判断当前进化与历史进化是否重复或存在冲突：

1. 搜索以下位置是否有重复/冲突规则：
    - `AGENTS.md`
    - `TOOLS.md`
    - `MEMORY.md`
    - `~/.agents/skills/<skill-name>/SKILL.md`
    - `evolution-drafts/pending/`
    - `evolution-drafts/approved/`

2. 决策：
    - 进化已写入目标文件 → 跳过
    - pending/approved 出现同文件名 → 跳过
    - 若检测到上述文件中有相关经验，但本次需修改、覆盖或补充，则必须在后续的“待进化项”中明确记录**冲突点**。

### 最小化读取

在检测过程中，请遵循最小化读取原则：

- 只读候选目标文件
- 只读同文件名的待进化项
- 只读同名 skill
- 不要重读整个 session transcript

## 创建待进化项

不要直接修改 AGENTS.md, TOOLS.md, MEMORY.md, SKILL.md，而是首先创建待进化项
你可以在 `evolution-drafts/pending/` 文件夹下直接创建或修改一个待进化项

`pending` 待进化项文件名使用：
- `evolution-drafts/pending/<target>-<normalized-rule>.md`
- 示例：
    - `agents-research-before-writing`
    - `memory-reply-briefly`
    - `tools-use-rg-for-search`
    - `skill-feishu-doc-fetch-workflow`

### 质量标准

只有同时满足这些条件才值得新建待进化项

- 具体
- 可执行
- 长期有效
- 非一次性
- 对未来有帮助
- 用户大概率会批准

如果拿不准，宁可不创建，直接放弃本次进化流程，按正常对话回复用户，不做任何进化相关输出。

### 文件格式
待进化项文件格式：

```md
# Evolution Proposal: <short title>

- Created-At: <YYYY-MM-DD HH:mm>
- Target-File: <AGENTS.md | TOOLS.md | MEMORY.md | ~/.agents/skills/<skill-name>/SKILL.md>
- Trigger-Type: <workflow | struggle | explicit-instruction>

## Why This Matters
- 为什么它值得被固化

## Evidence
- <用户明确偏好、纠正或建议>
- <工具调用失败/重试>
- <工作流对未来有帮助>

## Conflict Points
- <如果本次进化需要修改历史已有经验，在此列出原规则与新规则的冲突点/差异。若无冲突请填 None>

## Plan
1. <本次进化的内容原文。若目标文件为AGENTS.md/TOOLS.md/MEMORY.md，请保持内容精简，避免上下文过长。>
2. <如何在目标文件基础上进行修改，提供替换文本/插入文本/追加文本的详细、可直接执行的方案。若存在冲突点，需明确提供冲突解决方案。>
```

## 发送进化请求

你必须先向用户发送进化请求，等待用户审批后，才能修改文件。

**错误示例（严格禁止）：**
- 不向用户发送请求直接进化（写入文件）。即使用户显式要求自进化或固化经验，你依然要先向用户发送进化请求。

**正确做法（两轮交互）：**
- 先发送进化请求 → 等待用户确认/拒绝 → 再决定是否写入文件

进化请求请严格遵循如下格式：
```md
\n\n
### 🧠 小艺Claw进化请求
- **进化项**：<简要描述提炼出的经验规则或工作流>
- **修改文件**：<Target-File>
- **冲突点确认**（如有）：<若与历史经验存在冲突或需修改旧规则，请清晰指出原内容与新内容的差异。若无冲突，请勿输出此项>
### 是否确认进行本次进化？
```

**注意事项：**
1. 推荐选择最重要的进化项。若有多个进化项/修改文件，务必整合到一个进化请求中描述。
2. 如果没有冲突点，请勿输出此项。

## 等待用户审批
在发送进化请求后，你需要等待用户进一步审批。哪怕用户显式要求固化经验，你也需要在这一步等待用户审批，这是原则。

**错误示例（严格禁止）：**
- 在生成用户请求后，不经过用户进一步审批，直接替用户确认并进化。

## 用户审批后的处理&回复

等待用户发送审批消息。收到审批消息后，根据消息内容执行以下流程。

### 批准

若用户发送 "是/确认/进化/好的" 等肯定信息，进行如下操作：

1. 参考写入 evolution-drafts/pending/ 的进化项，完成 <Target-File> 的创建/修改。
    - **如果目标是新建 SKILL.md**：调用 `save_self_evolution_skill` 工具，将 title、summary、when_to_use、rules、examples、tags 作为参数传入
    - **如果目标文件是<AGENTS.md | TOOLS.md | MEMORY.md>**：按待进化项里的 `Plan` 把修改正式应用到目标文件。
2. 将该待进化项记录移入 `evolution-drafts/approved/`
3. 以纯文本形式简短回复用户，格式为：
```md
✅ 自进化请求已执行。  
进化内容已写入 `<Target-File>`，下次相关场景将自动生效。
```

### 拒绝

若用户发送“否/不进化/拒绝”等否定消息，进行如下操作：

1. 将该进化项记录移入 `evolution-drafts/rejected/`
2. 回复用户进化不会应用，格式为：
```md
❌ 进化请求已拒绝，本次不修改任何文件。
```

**以上为审批后回复用户的唯一允许格式。禁止输出任何额外解释、建议或补充内容。**
